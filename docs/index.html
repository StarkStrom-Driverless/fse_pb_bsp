fse_pb_bsp ist die Board Support Library für den STM32F405RTGE: Peripherie-Abstraktion, FreeRTOS, sicherer Bootloader und ein Tool, das Build, Flash und Debug auf einen Befehl reduziert.

Architektur

    
Zwei Stacks, ein Chip.

    
Die Library hängt am MCU-Bootloader. Deshalb gibt es zwei Pyramiden: links der Bootloader, rechts die Anwendung. Diese schreibst du in C oder baust sie als Simulink-Modell, das als generierter C-Code auf denselben Schichten läuft.

Bootloader

      
Basiert auf Zephyr mit MCUboot, gepflegt im eigenen Repo fse_pb_bootloader.
         Einmal geflasht, muss er normalerweise nie wieder angefasst werden.

      

        
Bootloader

        
Slot 0 läuft

        
Slot 1 Update

      

      
Liegt in Slot 1 ein gültiges, korrekt signiertes Image, tauscht der Bootloader Slot 0 und Slot 1 und startet dann. Standardmäßig läuft er aus Slot 0.

    

    

      
Anwendungs-Stack

      
libopencm3 konfiguriert die Hardware auf niedriger Ebene. fse_pb_bsp liefert
         darüber die Abstraktion für Controller-Konfiguration und kapselt außerdem FreeRTOS.

      
Darauf entsteht die eigentliche Anwendung, ohne Register oder RTOS-Details direkt anzufassen.

    

  


  

    
Simulink: vom Modell zur Firmware

    
Statt C zu schreiben, kannst du die Anwendung als Simulink-Modell bauen. Eigene ss_*-Blöcke (GPIO, ADC, PWM, CAN, Frequenzmessung, IOB, Queue) rufen im generierten Code die fse_pb_bsp-API auf. Das Modell läuft in einem eigenen RTOS-Task.

./ss build

          
Firmwarebp_test.elfCode wird automatisch mitkompiliert

Tooling

    
Alles läuft über ./ss.

    
Einmal pro Terminal-Sitzung das venv aktivieren, dann übernimmt ./ss. Ohne Argumente zeigt es die komplette Befehlsübersicht.

    
source .venv/bin/activate

  


  

    
./ss build
Baut die Haupt-Firmware (build/bp_test.elf).

    
./ss clean
Räumt den Build-Output der Haupt-Firmware auf.

    
./ss flash
Build, Signatur und Flash via OpenOCD/telnet in einem Schritt.

    
./ss canflash --bin_file <path> --id <hex id>
Flasht ein signiertes .bin über CAN.

    
./ss bootloader --bin_file <path> --position <addr>
Flasht ein Bootloader-Image, z. B. zephyr.bin.

    
./ss oocd_start | oocd_stop | oocd_state
Verwaltet den OpenOCD-Server. Danach öffnet make gdb ein GDB-TUI.

    
./ss  ·  ./ss gui
      
Dieselben Befehle als Fenster: Build, Flash und OpenOCD mit Flash- und RAM-Auslastung, die Beispiele samt Quelltext,
      der MATLAB-Workflow mit Statusübersicht und can_gen. Strg+C im Terminal schließt es.
      Benötigt imgui-bundle, das init.sh installiert.

Beispiele

    
Eine Peripherie, eine Datei.

    
fse_pb_bsp/examples/ enthält pro Peripherie ein minimales .c. Sie werden unabhängig von der Firmware gebaut und brauchen kein usr/. Am schnellsten geht es in der GUI: Beispiel wählen, Quelltext ansehen, mit einem Klick bauen und flashen.

  


  

    
./ss example_list
Alle verfügbaren Beispiele auflisten.

    
./ss example_build <name>
Ein Beispiel bauen, z. B. adc → examples/build/adc.elf.

    
./ss flash_example <name>
Bauen, signieren und via OpenOCD/telnet flashen.

  

  
Beide Build-Befehle geben den Pfad zur .c-Quelle aus, so springst du direkt in den Code. Ohne ./ss geht es auch:
    cd fse_pb_bsp/examples && make adc, make clean räumt auf.

Installation

    
Toolchain einrichten.

    
Am besten getestet unter Linux. Windows läuft nativ mit STM32CubeCLT (Build, Flash, Bootloader, MATLAB-Workflow), alternativ über WSL2. Dort kann USB-Passthrough beim Flashen Probleme machen; Fallback ist ein Release-Binary, das du direkt per st-link aus dem abgeleiteten Steuergeräte-Repo flashst.

  


  

    

      
      
      
    


    

      

        

          
Voraussetzungen

          
    
            
  1. 1
    STM32CubeCLT von st.com. Liefert arm-none-eabi-* und STM32_Programmer_CLI. Gesucht wird unter C:\ST und Program Files\ST, sonst per STM32CUBECLT_PATH setzen.
    2. 
            
  2. 2
    make.exe und sh.exe, z. B. aus dem xpack windows-build-tools-Archiv. Entpacken und bin\ in den PATH legen oder SS_MAKE auf make.exe zeigen lassen.
    3. 
            
  3. 3
    Python 3.10+ von python.org. Der Microsoft-Store-Stub funktioniert nicht.
    4. 
            
  4. 4
    Git für das Submodule.
    5. 
          

        

        

          
Ablauf


# im Projektordner, nach dem Quickstart (init.ps1)
.\ss.cmd build
.\ss.cmd flash
.\ss.cmd bootloader --bin_file zephyr.bin
.\ss.cmd clean

# optional: F5-Debugging in VS Code
code --install-extension marus25.cortex-debug

          
Flashen läuft über STM32_Programmer_CLI statt OpenOCD. Nur unter Linux gibt es canflash, die OpenOCD-Befehle, die Beispiel-Befehle und die GUI, dafür fehlt Windows SocketCAN. Bei langen Projektpfaden (> 80 Zeichen) kommt es zu MAX_PATH-Fehlern: Projekt näher an die Laufwerkswurzel legen oder Long Paths aktivieren.
