Architektur

Zwei Stacks, ein Chip.

Die Library hängt am MCU-Bootloader. Deshalb gibt es zwei Pyramiden: links der Bootloader, rechts die Anwendung. Diese schreibst du in C oder baust sie als Simulink-Modell, das als generierter C-Code auf denselben Schichten läuft.

Bootloader

Basiert auf Zephyr mit MCUboot, gepflegt im eigenen Repo fse_pb_bootloader. Einmal geflasht, muss er normalerweise nie wieder angefasst werden.

Bootloader
Slot 0 läuft
Slot 1 Update

Liegt in Slot 1 ein gültiges, korrekt signiertes Image, tauscht der Bootloader Slot 0 und Slot 1 und startet dann. Standardmäßig läuft er aus Slot 0.

Anwendungs-Stack

libopencm3 konfiguriert die Hardware auf niedriger Ebene. fse_pb_bsp liefert darüber die Abstraktion für Controller-Konfiguration und kapselt außerdem FreeRTOS.

Darauf entsteht die eigentliche Anwendung, ohne Register oder RTOS-Details direkt anzufassen.

Simulink: vom Modell zur Firmware

Statt C zu schreiben, kannst du die Anwendung als Simulink-Modell bauen. Eigene ss_*-Blöcke (GPIO, ADC, PWM, CAN, Frequenzmessung, IOB, Queue) rufen im generierten Code die fse_pb_bsp-API auf. Das Modell läuft in einem eigenen RTOS-Task.
